The Concept

Unreal Engine 5.7

Instead of creating a separate Blueprint asset for every weapon, potion, or piece of gear, each item is a row in a Data Table. The table defines everything about an item: its name, description, icon, category, stack limit, and which equipment slot it goes in. Adding a sword to the game means adding one row, not creating a new BP_Sword class.

Why Data Tables

  • Designers can add or tweak items in a spreadsheet without opening the Blueprint editor.
  • The same pickup actor handles every item type. No per-item Actor subclasses.
  • The UI reads from the same table to display names, icons, and descriptions - single source of truth.
  • Exporting and importing JSON means the item database can live outside the project (in a Google Sheet, say) and sync back in.
Same pattern as the Quest System. BP_YoteiGameInstance owns quest state; ItemManager will own inventory state. Both systems use Data Tables and event dispatchers so the UI never polls. Keeping the pattern consistent means the two systems will be easy to connect later, for example when a quest completion hands the player a reward item.

How It's Built

  • ItemManager is a Game Instance Subsystem. It is the only place the player's current inventory array lives.
  • Every widget that shows inventory data binds to OnItemAdded and OnItemRemoved dispatchers in Event Construct. No Tick reads.
  • Items are identified by their Data Table row name. The row name is what gets stored in the inventory array, not a full copy of the item struct.
  • Equipment state is a separate Map on the subsystem: slot enum to item row name. Equipping an item writes to the map and broadcasts OnEquipmentChanged.

Item Manager

Unreal Engine 5.7 Planning

ItemManager is a Game Instance Subsystem that owns the player's inventory array and broadcasts changes. Every other system calls into it - pickups call AddItem, the UI calls RemoveItem, and the equipment system calls EquipItem.

Core Functions (Planned)

AddItem(RowName, Quantity) - Find existing stack for this row name if stackable - If stack exists and has room: increment quantity - Else: add new inventory entry - Broadcast OnItemAdded RemoveItem(RowName, Quantity) - Find stack, decrement quantity - If quantity reaches 0: remove entry from array - Broadcast OnItemRemoved EquipItem(RowName) - Look up EquipSlot from Data Table row - If slot occupied: unequip current item first - Write to EquippedItems map (slot -> row name) - Broadcast OnEquipmentChanged UnequipItem(Slot) - Clear slot in EquippedItems map - Broadcast OnEquipmentChanged HasItem(RowName) -> Bool - Used by quests and triggers to check prerequisites

Subsystem Variables (Planned)

VariableTypeDescription
InventoryArray of F_InventoryEntryEach entry holds a row name and a quantity. This is the player's current items.
EquippedItemsMap of E_EquipSlot to NameWhat's currently equipped in each slot. Empty slots are absent from the map.
MaxCarryWeightFloatTotal carry limit. Set by character stats. Checked before AddItem completes.
OnItemAddedEvent DispatcherFired after any item is added. Passes the row name and new quantity.
OnItemRemovedEvent DispatcherFired after any item is removed. Passes row name.
OnEquipmentChangedEvent DispatcherFired when any equipment slot changes. Passes the slot enum.

Pickups

Unreal Engine 5.7 Planning

One generic pickup actor handles every item type. The only per-instance data it holds is the item's row name and a quantity. On interact, it calls ItemManager.AddItem and destroys itself.

BP_ItemPickup (Planned)

  • Exposes two variables in the editor: ItemRowName (Name) and Quantity (Integer, default 1). Both are instance-editable so level designers can drag one actor into the world and set which item it represents.
  • On BeginPlay: looks up the item's data in the table to pull the display name and mesh. Sets the StaticMeshComponent to whatever mesh is defined in the row. If no mesh is defined, falls back to a generic cube placeholder.
  • On Interact (called by the player's Interaction System): calls ItemManager.AddItem(ItemRowName, Quantity), plays a pickup sound/effect, then destroys self.
  • Optionally shows a floating label above the mesh with the item name pulled from the table. The label is a WBP_WorldLabel component.
Dependency: the pickup actor relies on the Interaction System from the Quest System being wired up. The same overlap/interact flow used by the Settler NPC trigger will drive pickup detection. No new input binding needed.

Inventory UI

Unreal Engine 5.7 Planning

The inventory screen lives inside the Pause Menu alongside the Quest Log, accessed via its own tab. It uses a two-panel layout: a grid of item slots on the left, a detail panel on the right.

Widget Hierarchy (Planned)

WBP_PauseMenu └── Widget Switcher (Tab index 2: Inventory) └── WBP_InventoryTab ├── Left: WBP_InventoryGrid │ └── Grid of WBP_InventorySlot (one per inventory entry) │ each slot shows the item icon and a quantity badge └── Right: WBP_ItemDetail shows name, description, category, weight and Equip / Use / Drop buttons based on item type

How Updates Work

  • WBP_InventoryTab binds to OnItemAdded and OnItemRemoved in Event Construct. When either fires, it rebuilds the grid.
  • WBP_ItemDetail is a persistent single instance, updated in place when the player clicks a slot. It never gets rebuilt - same pattern as WBP_QuestDetail in the Quest Log.
  • Clicking a slot passes the item row name to the detail panel. The panel looks up the full struct from the Data Table and populates its text and icon fields.
  • The Equip button is only visible for equippable items. The Use button only for consumables. The Drop button hidden for quest items. All of this is driven by the item's Category and IsQuestItem fields - no per-item widget variants.

Equipment Slots

Unreal Engine 5.7 Planning

Equipment slots define where an item lives on the character when equipped. The slot enum has one value per attachment point. Only one item can occupy a slot at a time. The ItemManager enforces this.

Equipment Slot Enum (Planned)

E_EquipSlot: PrimaryWeapon // right hand weapon SecondaryWeapon // left hand / shield Head Chest Hands Feet Accessory_1 Accessory_2

How It Works

  • When the player equips an item, ItemManager.EquipItem checks the item's EquipSlot field. If that slot already has something, it unequips that item first (moves it back to the inventory array) before writing the new one.
  • OnEquipmentChanged fires after every equip or unequip. The character's mesh component binds to this to attach or detach the item's skeletal mesh at the correct socket.
  • The equipment panel in the UI is a separate widget showing the character silhouette with slot targets. Clicking a slot opens the inventory filtered to items that fit that slot. Same data, different filter.
Dependency: visual mesh swapping requires sockets set up on the character's Skeletal Mesh. This can be stubbed with placeholder attachment logic (just attach a cube to a socket) and swapped for real meshes later. The data and event flow is independent of the visual result.

Roadmap

Unreal Engine 5.7

Build Order

  • Item Data Table: define the struct, populate a handful of test rows (a sword, a potion, a key item). Get the import pipeline working from JSON first.
  • ItemManager subsystem: the array, the Map, and the three dispatchers. No UI yet - test by printing to the screen from BeginPlay.
  • BP_ItemPickup: one actor, instance-editable row name. Drop it in the level, walk into it, confirm the item lands in the array via on-screen debug.
  • WBP_InventoryGrid + WBP_InventorySlot: build the grid, wire it to OnItemAdded / OnItemRemoved. Just icons and quantity for now.
  • WBP_ItemDetail: click a slot, see the item's name and description. Add the Equip / Use / Drop buttons.
  • Equipment slots: EquipItem logic, OnEquipmentChanged, stub visual attachment (cube on socket).
  • Equipment panel UI: character silhouette, slot targets, filtered inventory view.
  • Quest System integration: HasItem checks for quest prerequisites, AddItem called from quest completion rewards.

Dependency Order

Item Data Table + Struct | ItemManager Subsystem | BP_ItemPickup WBP_InventoryGrid | | +------- both need ItemManager wired first -------+ | WBP_ItemDetail | Equipment Slot Logic | Equipment Panel UI + Quest Integration

What This Unlocks

  • Quest rewards: a quest completion can hand the player an item by calling ItemManager.AddItem. The Quest System and Inventory System stay decoupled.
  • Ally gear: allies recruited via Side Quests can have loadouts driven by the same Data Table.
  • Shop system: a shop is just a UI that reads the item table and calls AddItem / RemoveItem with a currency check in front.
