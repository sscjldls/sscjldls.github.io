The Concept

Unity

Instead of writing a new script for every weapon, potion, or piece of gear, each item is a ScriptableObject asset. It carries everything: name, description, icon, category, stack limit, and equipment slot. Adding a sword to the game means creating one asset in the Project window, filling in the fields, and dropping it in the database. No code change.

Why ScriptableObjects

  • Item data lives in the Project window as serialized assets, not in a MonoBehaviour attached to a prefab.
  • One generic pickup prefab handles every item type. The only thing that changes per pickup is which ItemData ScriptableObject it references.
  • The UI reads directly from the same assets to display names, icons, and descriptions. Single source of truth, no sync required.
  • ScriptableObjects can be exported to JSON for external editing (a spreadsheet pipeline) and re-imported without touching the codebase.

How It's Built

  • InventoryManager is a persistent singleton that survives scene loads. It is the only place the player's current inventory list lives at runtime.
  • Every UI panel that shows inventory data subscribes to OnItemAdded and OnItemRemoved C# events in OnEnable. No Update polling.
  • Items are identified by their ItemData ScriptableObject reference. The inventory list stores the reference and a quantity, not a copy of the data.
  • Equipment state is a separate Dictionary on the manager: slot enum to ItemData reference. Equipping writes to the Dictionary and fires OnEquipmentChanged.

Item Manager

Unity Planning

InventoryManager is a persistent singleton MonoBehaviour that survives scene loads. It owns the player's inventory list and fires C# events when it changes. Everything else - pickups, UI, equipment - calls into it or subscribes to it.

Core Functions (Planned)

AddItem(ItemData item, int quantity) - Find existing InventoryEntry for this item if stackable - If entry exists and has room: increment quantity - Else: add new InventoryEntry to the list - Fire OnItemAdded event RemoveItem(ItemData item, int quantity) - Find entry, decrement quantity - If quantity reaches 0: remove entry from list - Fire OnItemRemoved event EquipItem(ItemData item) - Read item.EquipSlot - If slot occupied: call UnequipItem(slot) first - Write to EquippedItems dict (slot -> ItemData) - Fire OnEquipmentChanged event UnequipItem(EquipSlot slot) - Remove slot key from EquippedItems dict - Fire OnEquipmentChanged event HasItem(ItemData item) -> bool - Returns true if item exists in inventory list

Manager Variables (Planned)

VariableTypeDescription
inventoryList<InventoryEntry>Each entry holds an ItemData reference and a quantity. The player's current items.
equippedItemsDictionary<EquipSlot, ItemData>What's currently equipped in each slot. Empty slots have no key.
maxCarryWeightfloatTotal carry limit. Set by character stats. Checked before AddItem completes.
OnItemAddedAction<ItemData, int>Fired after any item is added. Passes the item and new total quantity.
OnItemRemovedAction<ItemData>Fired after any item is removed.
OnEquipmentChangedAction<EquipSlot>Fired when any equipment slot changes. Passes the affected slot.

Pickups

Unity Planning

One generic pickup prefab handles every item type. The only per-instance data it holds is which ItemData asset it represents and a quantity. On interact, it calls InventoryManager.AddItem and destroys itself.

ItemPickup (Planned)

  • Two serialized fields in the Inspector: itemData (ItemData ScriptableObject) and quantity (int, default 1). Drag the prefab into the scene, assign the asset, done.
  • On Start: reads itemData to pull the display name and optional world mesh. If no mesh is assigned, falls back to a placeholder capsule.
  • On trigger enter or interact: calls InventoryManager.Instance.AddItem(itemData, quantity), plays a pickup sound, then calls Destroy(gameObject).
  • Optionally renders a floating world-space label showing the item name via a Billboard Canvas child object.
Interaction approach TBD: deciding between trigger-based auto-pickup (walk into it to collect) and a dedicated interact input (press E). Trigger-based is faster to build; interact input matches the feel of most RPGs. Will decide once the player controller is further along.

Inventory UI

Unity Planning

The inventory screen opens on a pause input. It uses a two-panel layout: a grid of item slots on the left, a detail panel on the right. Built with Unity's UI Toolkit or uGUI - not decided yet.

UI Structure (Planned)

InventoryScreen (Canvas) ├── Left: InventoryGrid │ └── ItemSlot x N (one per inventory entry) │ each slot shows the item Icon (Sprite) and a quantity badge └── Right: ItemDetailPanel shows name, description, category, weight and Equip / Use / Drop buttons depending on item type

How Updates Work

  • InventoryGrid subscribes to InventoryManager.OnItemAdded and OnItemRemoved in OnEnable (unsubscribes in OnDisable). When either fires, it rebuilds the slot list.
  • ItemDetailPanel is a persistent single instance, updated in place when the player clicks a slot. It never gets destroyed and recreated.
  • Clicking a slot passes the ItemData reference to the detail panel. The panel reads directly from the asset to populate text and icon.
  • The Equip button is only active for equippable items. Use only for consumables. Drop hidden for key items. All driven by itemData.Category and itemData.IsKeyItem - no per-item UI variants.

Equipment Slots

Unity Planning

Equipment slots define where an item lives on the character when equipped. One item per slot, enforced by InventoryManager. The slot enum maps directly to Transform attachment points on the character rig.

Equipment Slot Enum (Planned)

public enum EquipSlot { PrimaryWeapon, // right hand SecondaryWeapon, // left hand / shield Head, Chest, Hands, Feet, Accessory1, Accessory2 }

How It Works

  • When the player equips an item, InventoryManager.EquipItem checks itemData.EquipSlot. If that slot is occupied, the current item gets moved back to the inventory list before the new one writes in.
  • OnEquipmentChanged fires after every equip or unequip. A CharacterEquipment MonoBehaviour subscribes to this event and handles the visual: instantiating the item's prefab at the matching child Transform on the rig.
  • The equipment panel in the UI shows slot targets arranged around a character silhouette. Clicking a slot opens the inventory grid filtered to items whose EquipSlot matches. Same data, different filter.
Dependency: visual swapping requires named child Transforms on the character rig (e.g. "RightHandAttach"). This can be stubbed early with a placeholder cube at each point and swapped for real meshes later. The data layer and events work independently of the visual result.

Roadmap

Unity

Build Order

  • ItemData ScriptableObject: define the class, create a handful of test assets (a sword, a potion, a key item). Confirm they serialize correctly in the Inspector.
  • InventoryManager singleton: the list, the Dictionary, and the three C# events. No UI yet - test by calling AddItem from a debug key and logging the list to the console.
  • ItemPickup prefab: one prefab, ItemData field in the Inspector. Drop it in a test scene, walk into it, confirm the item lands in the list via console log.
  • InventoryGrid + ItemSlot UI: build the grid, wire it to OnItemAdded / OnItemRemoved. Just icons and quantity badges for now.
  • ItemDetailPanel: click a slot, see name and description. Add the Equip / Use / Drop buttons with correct visibility per category.
  • Equipment slot logic: EquipItem, OnEquipmentChanged, stub visual attachment (cube at a named Transform on the rig).
  • Equipment panel UI: character silhouette, slot targets, filtered inventory view.
  • Shop system: a separate scene object or NPC that opens a filtered view and calls AddItem / RemoveItem with a currency check.

Dependency Order

ItemData ScriptableObject | InventoryManager (singleton) | ItemPickup Prefab InventoryGrid UI | | +---- both need InventoryManager wired first ----+ | ItemDetailPanel UI | Equipment Slot Logic | Equipment Panel UI + Shop

What This Unlocks

  • Shop system: a shop is just a UI that reads from ItemData assets and calls AddItem / RemoveItem with a currency check in front.
  • Crafting: a recipe is a list of ItemData inputs and one ItemData output. The crafting system calls HasItem, RemoveItem, then AddItem.
  • Loot tables: enemies drop pickups by picking from a weighted list of ItemData references. No per-enemy item code needed.
